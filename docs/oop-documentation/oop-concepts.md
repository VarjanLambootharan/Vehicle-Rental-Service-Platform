# Nine OOP concepts in the implemented code

1. **Encapsulation:** Entity identifiers/timestamps and business state are private. `Booking.start`, `complete`, `requestCancellation`, `finishCancellation`, `Payment.transitionPending` and `settleCancellation` control valid changes. No unrestricted booking/payment state or amount setters exist. Services coordinate cross-record invariants under the storage lock.
2. **Inheritance:** abstract `User` holds shared identity, contact, password hash and active state; `Customer` and `Admin` specialize it. Abstract `Vehicle` holds registration, pricing and administrative state; `Car` and `Motorcycle` specialize it. `EventEntity` extends `Entity`, and Booking/Payment/Review inherit persistent event behavior.
3. **Polymorphism:** `VehicleCatalogue.search` invokes `passengerCapacity()` on `Vehicle` references. Cars return their seat count; motorcycles allow two occupants. `VehicleResponse.from` calls overridden `rentalGuidance()` so rental instructions reflect car transmission/occupants or motorcycle engine/licence/helmet requirements. `User.getRole()` is likewise overridden rather than client-settable.
4. **Abstraction:** `User` and `Vehicle` define common behavior without being directly instantiable. `TextRepository<T>` abstracts repeated record persistence; repositories expose domain-typed operations. Services work through repository methods instead of knowing the text codec, streams, temporary files or atomic moves.
5. **Information hiding:** `TextFileStore` keeps its directory and replacement implementation private. DTOs expose an explicit API contract; they omit password hashes, private source events and processed payment workflow bookkeeping. `EventEntity.getEvents()` returns an immutable copy of its event list.
6. **Composition:** a Booking owns one immutable `RentalPeriod`. The booking constructor requires a valid value, date modifications replace it, and it is serialized as a nested object. A period has no independent ID, repository or storage file. There are no duplicate flat pickup/return fields in a booking. The cancellation workflow and source event list are also owned parts of their records.
7. **Aggregation:** `VehicleCatalogue` groups existing vehicle objects through a copied collection. It does not create, save or delete them. A vehicle survives independently of any catalogue instance and remains in `vehicles.txt`.
8. **Association:** Booking holds customerId and vehicleId; Payment holds bookingId/customerId; MaintenanceRecord holds vehicleId; Review holds customerId/vehicleId/bookingId. These UUID associations are validated through repositories and service rules; they are not embedded copies of customer or vehicle objects.
9. **Dependency:** Spring constructor injection builds `BookingController → BookingService → BookingRepository → TextFileStore`. The service also depends on `AvailabilityService`, `StorageCoordinator`, `Access`, the business `Clock`, payment/vehicle repositories and `NotificationService`. Required dependencies are explicit and replaceable in tests. Production services never instantiate repositories manually.
